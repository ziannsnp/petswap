# ADR 0008: Self-contained Docker Compose stack alongside the Supabase CLI

**Status:** Accepted

## Context

Local development runs the backend with `npx supabase start` ([ADR 0004](0004-supabase-mvp-foundation.md)), which needs Node, the Supabase CLI, and several documented manual steps. The Sprint 1 regression run showed how that goes wrong: one undocumented step (the `sign-in` function's origin allowlist) left username sign-in silently broken on an otherwise working setup. US-D.3 asks that PetSwap come up the same way after setup or recovery, from documented settings, with a check that says so.

Three ways to get there were considered:

- **Wrap the CLI in a script.** Smallest change, but still needs Node and the CLI on the machine, and the CLI chooses image versions per release, so two machines can run different backends.
- **Run the CLI inside a Compose service with the Docker socket mounted.** One command, but the CLI bind-mounts host paths that do not exist from inside a container on Windows and macOS.
- **Define the services directly in Compose.** More to maintain, but it needs only Docker, pins every image, and takes every setting from one file.

## Decision

Add `docker-compose.yml`: the production build of the web app served by nginx, plus only the Supabase services the app calls — Postgres, Auth, PostgREST, Storage, the Edge Runtime for `sign-in`, and the Kong gateway. A one-shot job applies `supabase/migrations/` and, on a new database, `supabase/seed.sql`. Every setting comes from `.env`, documented in `.env.example` and generated by `scripts/stack-env.sh`; `scripts/stack-health.sh` verifies the result.

The stack does not replace `supabase start`. The CLI stays the tool for writing migrations, regenerating types, Studio, and the database contract workflow. Migrations and `supabase/config.toml` remain the single source for schema and backend behaviour; the Compose file follows them.

## Consequences

Anyone with Docker gets a working PetSwap from three commands, and a wiped machine gets the identical one back.

Auth, API, and storage settings now exist twice: in `supabase/config.toml` for the CLI and as service environment in `docker-compose.yml`. A change to one must be made in the other in the same pull request. Image tags are pinned by hand and must be bumped deliberately, to the versions the team's CLI release runs.

The stack publishes the same ports as `supabase start`, so only one runs at a time. Realtime, Studio, the mail catcher, and image transforms are absent; a feature that needs one must add the service here as well as use it.

The stack binds to `127.0.0.1` and seeds test accounts by default. It is a local and recovery tool, not a hosting decision: production stays on Cloudflare and the hosted Supabase project ([ADR 0005](0005-cloudflare-workers-hosting.md)). Serving this stack publicly needs its own decision covering TLS, secrets, mail, and backups.
